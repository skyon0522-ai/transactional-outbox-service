Demo checks passed

One purchase, two transaction boundaries. The producer stores an order and its outbox event together. A separate relay delivers the event; the receiver stores its receipt and fulfillment together.

The duplicate check explicitly replays the same bytes over HTTP after the relay acknowledges delivery. It does not simulate a lost response. The separate restart verification covers that failure mode.

Keep or inspect the evidence

result.json is the machine-readable completion marker: only status: passed means the whole run, including owned-process shutdown, finished. A missing file or any other status is incomplete.

producer.sqlite retains the order, message log and acknowledged offset. receiver.sqlite retains the receipt, fulfillment and delivery count. *.stdout, *.stderr and *.log retain command and process output.

What this example establishes

The observed checks cover one sequential producer and one relay on local SQLite files with fixed synthetic data. Repeated byte-identical delivery creates one fulfillment. This is at-least-once delivery with receiver deduplication; it does not establish exactly-once transport, power-loss recovery, concurrent-writer safety or production readiness.

All child processes use numeric loopback addresses. The runner opens no browser and sends no data to an external service. This file works offline without JavaScript.
